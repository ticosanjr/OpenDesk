Especificação Técnica e Arquitetural Completa: OpenDesk (SPEC.md)
Instrução para o Agente Desenvolvedor: Este documento é a especificação mestre de engenharia (SRS + Blueprint de Implementação) do OpenDesk. Siga estritamente a arquitetura, contratos de dados, schemas SQLite, estruturas Rust e diretrizes de sincronização descritas abaixo. Não crie abstrações proprietárias que substituam os arquivos nativos do OpenCode no disco.
1. Visão Geral do Sistema e Leis Arquiteturais
O OpenDesk é um aplicativo desktop nativo ultraleve e daemon de bandeja de sistema (system tray) escrito em Rust (Tauri v2 + Tokio + Axum + SQLx) com interface React + TypeScript + Tailwind CSS + Shadcn/UI (estética minimalista Dark Mode inspirada no Linear/Raycast).
Ele funciona como um Sistema Operacional Visual de Governança, Automação e Observabilidade sobre o OpenCode (opencode serve --port 3100).
As 4 Leis Invioláveis do OpenDesk
1. Zero Abstraction Layer (SSOT no Disco): O sistema de arquivos local é a única fonte da verdade para configurações do OpenCode. Workspaces, opencode.jsonc, .opencode/agents/*.md, .opencode/skills/*/SKILL.md e .opencode/commands/*.md são lidos e gravados diretamente no disco. Tudo o que é criado no OpenDesk aparece instantaneamente na CLI/TUI do OpenCode e vice-versa.
2. Loop de Inferência Delegado ao OpenCode: O OpenDesk nunca implementa seu próprio loop de execução de ferramentas de baixo nível. Toda execução de tarefa é enviada via HTTP/SSE para o daemon opencode serve ([http://127.0.0.1:3100](http://127.0.0.1:3100)), garantindo que o harness nativo do OpenCode gerencie o acesso a arquivos, bash e MCPs.
3. Roteamento Modular Estilo DSH (dsh-superagent-prototype): Antes de enviar uma tarefa complexa ao OpenCode, o DSH Router Engine do OpenDesk classifica a intenção, separa o ciclo em fases (Plan ➔ Build ➔ Audit), seleciona o modelo e nível de esforço (effort: low | medium | high) com base na política ativa (Melhor Custo-Benefício, Mais Barato, Máxima Qualidade, Manual ou Regras Customizadas) e empacota apenas o contexto limpo necessário para cada subagente.
4. Entrega Determinística de Artefatos: Toda tarefa ou rotina agendada possui diretórios de saída previsíveis (<workspace>/output/YYYY-MM/<task-slug>/), rastreamento de proveniência (quem criou, por quê, quando, em qual tarefa) e gatilhos pós-execução (envio por SMTP/Gmail, criação de Google Docs, upload no Google Drive e eventos no Google Calendar).
2. Stack Tecnológica e Estrutura do Repositório
2.1. Stack Definida
* Core / Daemon / Desktop Shell: Rust (Edition 2024), Tauri v2 (com suporte a tray-icon, single-instance, notification, shell), Tokio (async runtime), Axum (API local + WebSocket /ws para sincronização em tempo real).
* Manipulação de Arquivos e Configs:
   * notify (watcher de sistema de arquivos inotify/FSEvents para sincronização bidirecional instantânea).
   * jsonc-parser / serde_json (leitura e edição cirúrgica da AST do opencode.jsonc preservando comentários e formatação).
   * gray_matter / serde_yaml (parser e gerador de frontmatter YAML para .opencode/agents/*.md, skills e commands).
* Persistência Operacional: SQLite embarcado via sqlx (modo WAL ativado), armazenando fila, histórico de execuções, proveniência de artefatos, agendamentos cron, telemetria de custos e credenciais criptografadas.
* Agendador e Fila: tokio-cron-scheduler + fila prioritária em memória persistida no SQLite controlada por tokio::sync::Semaphore e CancellationToken.
* Integrações Externas:
   * lettre (cliente SMTP assíncrono em Rust com suporte a TLS, HTML e anexos).
   * oauth2 +  keyring (autenticação OAuth2 nativa com Google Workspace armazenando tokens no chaveiro seguro do SO).
   * Clientes REST Google APIs (reqwest): Google Drive v3, Google Docs v1, Google Calendar v3, Gmail v1, Google Keep / Tasks API.
* Frontend: React 19, TypeScript 5, Vite, Tailwind CSS v4, Shadcn/UI, Lucide Icons, Zustand (gerenciamento de estado sincronizado via WS), @dnd-kit (Kanban drag-and-drop), Recharts (gráficos de telemetria e gastos), Monaco Editor / CodeMirror (edição rápida de Markdown/JSONC e visualizador de Diffs).

3. Sincronização Bidirecional e Formatos Nativos do OpenCode (SSOT)
O módulo config_sync deve ler e escrever diretamente nos caminhos padrão do OpenCode:
* Escopo Global: ~/.config/opencode/ (opencode.jsonc, agents/, skills/, commands/).
* Escopo do Workspace Ativo: <workspace_path>/.opencode/ e <workspace_path>/opencode.jsonc.
3.1. Manipulação do opencode.jsonc (jsonc_editor.rs)
Deve usar jsonc_parser::cst::CstRootNode para modificar chaves sem apagar comentários existentes. A interface do OpenDesk deve permitir criar, editar e remover todas as propriedades abaixo:






Code snippet
{
 "$schema": "https://opencode.ai/config.json",
 // Modelo principal e modelo leve padrão do workspace
 "model": "opencode-go/deepseek-v4.1-flash",
 "small_model": "opencode-go/deepseek-v4.1-flash",
 // Permissões globais de execução
 "permission": {
   "edit": "allow",
   "bash": "ask",
   "webfetch": "allow"
 },
 // Regras do File Watcher nativo
 "watcher": {
   "ignore": ["node_modules/**", "target/**", ".git/**", ".opendesk/**"]
 },
 // Comandos customizados iniciados por /
 "command": {
   "auditar": {
     "template": "Analise o arquivo $ARGUMENTS e valide falhas lógicas.",
     "description": "Auditoria técnica rigorosa",
     "agent": "auditor",
     "model": "opencode-go/glm-5.3"
   }
 },
 // Servidores MCP (locais stdio e remotos sse)
 "mcp": {
   "google-workspace": {
     "type": "local",
     "command": ["opendesk-mcp-bridge", "--service", "google"],
     "enabled": true,
     "environment": {
       "WORKSPACE_ID": "default"

   }
 }
}

3.2. Formato dos Agentes e Subagentes (.opencode/agents/<slug>.md)
O OpenDesk deve ler todos os arquivos .md em ~/.config/opencode/agents/ e <workspace>/.opencode/agents/, parsear o frontmatter YAML e exibi-los na UI. Quando o usuário criar ou editar um agente na UI (ou pedir pelo chat), o OpenDesk grava exatamente neste formato:






Markdown
---
description: Especialista em auditoria de qualidade e verificação de fatos
mode: subagent
model: opencode-go/glm-5.3
temperature: 0.1
tools:
 write: false
 edit: false
 bash: false
 read: true
permission:
 edit: deny
  bash: deny
---
Você é o Auditor de Qualidade do workspace.
Sua função é inspecionar os artefatos gerados, apontar alucinações e validar contra os requisitos originais.

Nota sobre mode: primary (agentes principais como build e plan, alternáveis via Tab no OpenCode), subagent (invocáveis via @nome) ou all.
3.3. Formato das Skills (.opencode/skills/<skill-slug>/SKILL.md)
Cada skill reside em seu próprio subdiretório contendo SKILL.md e eventuais scripts/templates auxiliares:






Markdown
---
name: relatorio-executivo
description: Padroniza a geração de relatórios executivos com tabelas e métricas verificáveis
---
# Instruções da Skill: Relatório Executivo
1. Sempre inicie com um bloco TL;DR de no máximo 3 linhas.
2. Salve o resultado final no diretório determinístico informado no prompt.
3. Nunca utilize termos vagos sem apresentar o número exato.

3.4. Sincronização em Tempo Real (watcher.rs)
* Ao detectar qualquer evento Create, Modify ou Remove nas pastas .opencode/ ou na pasta output/ do workspace via crate notify (com debounce de 150ms), o backend atualiza o índice em memória e emite um frame WebSocket FS_SYNC_EVENT para o frontend atualizar a UI instantaneamente.
4. Integração com OpenCode Server (:3100) e Interceptação de Artefatos
4.1. Gerenciador do Daemon (daemon_manager.rs)
* No boot do OpenDesk, verifica se [http://127.0.0.1:3100](http://127.0.0.1:3100) está respondendo.
* Se não estiver ativo, o OpenDesk inicia automaticamente um processo filho gerenciado: opencode serve --hostname 127.0.0.1 --port 3100.
* Mantém um loop de heartbeat a cada 5 segundos e exibe o indicador luminoso (Verde = Online, Amarelo = Ocupado, Vermelho = Offline/Reiniciando) no ícone da bandeja do sistema e no topo da UI.
4.2. Execução e Interceptação de Tool Calls (stream_interceptor.rs)
Quando uma tarefa da fila entra em execução:
1. O OpenDesk faz POST na API de sessão/execução do OpenCode Server passando o diretório do workspace (cwd), o agente selecionado (agent), o modelo (model) e o prompt estruturado.
2. O OpenDesk consome o stream SSE de eventos em tempo real.
3. Interceptação de Artefatos: Toda vez que o stream SSE reportar a execução de uma ferramenta de escrita/edição de arquivo (write, edit, patch ou criação via bash), o stream_interceptor captura:
   * file_path: Caminho do arquivo modificado/criado.
   * agent_name: Qual agente ou subagente executou a ação.
   * task_id & run_id: Vínculo com o card do Kanban ou rotina agendada.
   * reason_summary: Resumo extraído da mensagem imediatamente anterior à chamada da ferramenta.
   * diff_patch: O diff antes/depois da modificação.
4. Esses dados são gravados imediatamente na tabela artifacts_provenance, alimentando a visão Lista de Artefatos Criados.
5. Roteador Modular de Tarefas (Inspirado no dsh-superagent-prototype)
O módulo dsh_router implementa a arquitetura de superagente modular em 4 camadas antes ou durante a chamada ao OpenCode:

5.1. Estratégias de Roteamento Configuráveis na UI
O usuário pode selecionar o modo global do roteador ou definir regras condicionais:
1. Modo Manual: O usuário escolhe no dropdown exatamente o modo (plan ou build), o subagente (@), o modelo (lista dinâmica carregada de :3100/v1/models) e o effort (low, medium, high).
2. Modo Mais Barato (Budget Mode): Roteia 100% das tarefas para opencode-go/deepseek-v4.1-flash com effort: low.
3. Modo Melhor Custo-Benefício (Default DSH):
   * Triagem, classificação, resumo, formatação e leitura de dados ➔ opencode-go/deepseek-v4.1-flash (effort: low).
   * Fase Plan (arquitetura, decomposição de etapas) ➔ opencode-go/glm-5.3 (effort: medium).
   * Fase Build (escrita complexa, refatoração de código, auditoria crítica) ➔ opencode-go/glm-5.3 ou opencode-go/deepseek-v4-pro (effort: high).
4. Modo Máxima Qualidade: Executa obrigatoriamente em 3 estágios encadeados: Plan (deepseek-v4-pro) ➔ Build (glm-5.3) ➔ Review/Audit (@auditor com deepseek-v4-pro).
5. Motor de Regras Customizadas (IF-THEN): A UI permite criar regras avaliadas em ordem de prioridade:
   * Exemplo 1: SE task.tags CONTAINS 'roteiro' ENTÃO mode = 'build', agent = '@roteirista', model = 'opencode-go/glm-5.3', effort = 'high'.
   * Exemplo 2: SE budget.daily_spent_pct > 80% ENTÃO FORÇAR model = 'opencode-go/deepseek-v4.1-flash', effort = 'low'.
   * Exemplo 3: SE task.EstimatedComplexity == 'HIGH' ENTÃO EXECUTAR Plan antes de Build (move o card para coluna Review aguardando clique humano de aprovação do plano antes de rodar o Build).
5.2. Meta-Builder: Criação de Agentes, Skills e Comandos por Pedido (meta_builder.rs)
Quando o usuário digita no chat ou na barra de comando:
* "Crie um subagente chamado @revisor-fiscal focado em contabilidade italiana forfettaria que só pode ler arquivos e usar busca web, usando o modelo glm-5.3" O meta_builder intercepta o pedido, gera o arquivo .opencode/agents/revisor-fiscal.md validado, salva no disco e retorna no chat o card interativo do novo agente já pronto para uso. O mesmo vale para criação de Skills (.opencode/skills/<nome>/SKILL.md), Comandos (/) e registro de servidores MCP no opencode.jsonc.
6. Schema Completo do Banco de Dados (SQLite - 0001_initial_schema.sql)
O banco SQLite fica em ~/.local/share/opendesk/opendesk.db (ou %APPDATA%/opendesk/opendesk.db).






SQL
PRAGMA journal_mode = WAL;
PRAGMA foreign_keys = ON;

-- 1. Workspaces (Empresas / Áreas / Projetos)
CREATE TABLE workspaces (
   id TEXT PRIMARY KEY,
   name TEXT NOT NULL,
   root_path TEXT NOT NULL UNIQUE,
   description TEXT,
   color_hex TEXT DEFAULT '#3b82f6',
   default_router_policy TEXT CHECK(default_router_policy IN ('COST_BENEFIT', 'CHEAPEST', 'BEST_QUALITY', 'MANUAL', 'CUSTOM_RULES')) DEFAULT 'COST_BENEFIT',
   default_email_recipient TEXT,
   google_drive_folder_id TEXT,
   is_active BOOLEAN DEFAULT 1,
   created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
   last_opened_at DATETIME DEFAULT CURRENT_TIMESTAMP
);

-- 2. Tarefas do Kanban
CREATE TABLE tasks (
   id TEXT PRIMARY KEY,
   workspace_id TEXT NOT NULL REFERENCES workspaces(id) ON DELETE CASCADE,
   title TEXT NOT NULL,
   description TEXT NOT NULL,
   column_stage TEXT CHECK(column_stage IN ('BACKLOG', 'PLAN', 'BUILD', 'REVIEW', 'DONE')) DEFAULT 'BACKLOG',
   priority INTEGER DEFAULT 2, -- 1: Baixa, 2: Normal, 3: Alta, 4: Crítica
   execution_mode TEXT CHECK(execution_mode IN ('AUTO_DSH', 'PLAN_ONLY', 'BUILD_DIRECT', 'PLAN_THEN_BUILD')) DEFAULT 'AUTO_DSH',
   assigned_agent TEXT,        -- Ex: 'researcher', 'auditor' ou NULL (decidido pelo Router)
   preferred_model TEXT,       -- Ex: 'opencode-go/deepseek-v4.1-flash' ou NULL
   effort_level TEXT CHECK(effort_level IN ('low', 'medium', 'high')) DEFAULT 'medium',
   plan_markdown TEXT,         -- Plano gerado na fase PLAN para aprovação
   output_dir_path TEXT,       -- Pasta determinística onde os resultados finais estão salvos
   notify_email TEXT,          -- Se preenchido, dispara e-mail ao concluir
   export_to_gdocs BOOLEAN DEFAULT 0,
   tags_json TEXT DEFAULT '[]',
   position_index INTEGER DEFAULT 0,
   created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
   updated_at DATETIME DEFAULT CURRENT_TIMESTAMP
);

-- 3. Fila de Execução e Comandos
CREATE TABLE execution_queue (
   id TEXT PRIMARY KEY,
   workspace_id TEXT NOT NULL REFERENCES workspaces(id) ON DELETE CASCADE,
   task_id TEXT REFERENCES tasks(id) ON DELETE SET NULL,
   schedule_id TEXT REFERENCES schedules(id) ON DELETE SET NULL,
   prompt_payload TEXT NOT NULL,
   resolved_mode TEXT NOT NULL,   -- 'plan' ou 'build'
   resolved_agent TEXT NOT NULL,
   resolved_model TEXT NOT NULL,
   resolved_effort TEXT NOT NULL,
   priority INTEGER DEFAULT 2,
   status TEXT CHECK(status IN ('QUEUED', 'RUNNING', 'PAUSED', 'COMPLETED', 'FAILED', 'CANCELLED')) DEFAULT 'QUEUED',
   retry_count INTEGER DEFAULT 0,
   max_retries INTEGER DEFAULT 2,
   error_message TEXT,
   enqueued_at DATETIME DEFAULT CURRENT_TIMESTAMP,
   started_at DATETIME,
   finished_at DATETIME
);

-- 4. Histórico de Runs e Telemetria Financeira
CREATE TABLE task_runs (
   id TEXT PRIMARY KEY,
   queue_job_id TEXT REFERENCES execution_queue(id) ON DELETE SET NULL,
   workspace_id TEXT NOT NULL REFERENCES workspaces(id) ON DELETE CASCADE,
   task_id TEXT REFERENCES tasks(id) ON DELETE SET NULL,
   agent_name TEXT NOT NULL,
   execution_mode TEXT NOT NULL,
   model_id TEXT NOT NULL,
   effort_level TEXT NOT NULL,
   status TEXT CHECK(status IN ('RUNNING', 'SUCCESS', 'FAILED', 'CANCELLED')) NOT NULL,
   tokens_input INTEGER DEFAULT 0,
   tokens_output INTEGER DEFAULT 0,
   tokens_cache_read INTEGER DEFAULT 0,
   tokens_cache_write INTEGER DEFAULT 0,
   estimated_cost_usd REAL DEFAULT 0.0,
   duration_ms INTEGER DEFAULT 0,
   raw_stdout_log TEXT,
   summary_response TEXT,
   started_at DATETIME DEFAULT CURRENT_TIMESTAMP,
   completed_at DATETIME
);

-- 5. Proveniência de Artefatos (Separado do File Explorer)
CREATE TABLE artifacts_provenance (
   id TEXT PRIMARY KEY,
   workspace_id TEXT NOT NULL REFERENCES workspaces(id) ON DELETE CASCADE,
   task_id TEXT REFERENCES tasks(id) ON DELETE SET NULL,
   run_id TEXT NOT NULL REFERENCES task_runs(id) ON DELETE CASCADE,
   file_path TEXT NOT NULL,         -- Caminho relativo ao workspace
   absolute_path TEXT NOT NULL,
   file_type TEXT NOT NULL,         -- 'md', 'json', 'py', 'rs', 'pdf', etc.
   file_size_bytes INTEGER DEFAULT 0,
   action_type TEXT CHECK(action_type IN ('CREATED', 'MODIFIED', 'DELETED')) NOT NULL,
   created_by_agent TEXT NOT NULL,  -- Qual agente criou/modificou
   creation_reason TEXT NOT NULL,   -- Por que foi criado (intenção da etapa/prompt)
   diff_patch TEXT,                 -- Diff unificado da alteração
   google_doc_url TEXT,             -- Link se foi exportado para o Google Docs
   google_drive_url TEXT,           -- Link se foi enviado ao Drive
   emailed_to TEXT,                 -- Destinatários caso tenha sido enviado por e-mail
   created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);

-- 6. Agendador de Rotinas Recorrentes (Cron)
CREATE TABLE schedules (
   id TEXT PRIMARY KEY,
   workspace_id TEXT NOT NULL REFERENCES workspaces(id) ON DELETE CASCADE,
   name TEXT NOT NULL,
   description TEXT,
   cron_expression TEXT NOT NULL,   -- Ex: '0 8 * * 1-5'
   agent_name TEXT,                 -- Subagente específico ou NULL para Router DSH
   command_or_prompt TEXT NOT NULL, -- Pode ser '/relatorio-diario' ou prompt completo
   router_policy TEXT DEFAULT 'COST_BENEFIT',
   output_folder_template TEXT DEFAULT 'output/{YYYY}-{MM}/{schedule_slug}',
   notify_email_recipients TEXT,    -- Lista separada por vírgula
   sync_to_google_docs BOOLEAN DEFAULT 0,
   sync_to_google_calendar BOOLEAN DEFAULT 0,
   is_active BOOLEAN DEFAULT 1,
   last_run_at DATETIME,
   last_run_status TEXT,
   next_run_at DATETIME,
   created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);

-- 7. Regras do Roteador DSH e Limites de Orçamento (Budget Guard)
CREATE TABLE router_rules (
   id TEXT PRIMARY KEY,
   workspace_id TEXT REFERENCES workspaces(id) ON DELETE CASCADE, -- NULL = Global
   name TEXT NOT NULL,
   priority_order INTEGER NOT NULL,
   condition_json TEXT NOT NULL,    -- Ex: {"field": "tags", "op": "contains", "value": "code"}

7. Gestão de Arquivos Determinística, E-mail e Google Workspace
7.1. Padronização Automática de Pastas de Saída
Para eliminar a bagunça de arquivos perdidos:
* Todo workspace inicializado ou importado no OpenDesk recebe uma estrutura limpa (criada sob demanda):
   * <workspace>/input/ (arquivos de entrada e referências).
   * <workspace>/output/<YYYY>-<MM>/<data_slug_tarefa>/ (resultados finais gerados pelos agentes).
* Quando o OpenDesk despacha uma tarefa para o OpenCode no modo Build ou via Schedule, o context_packer injeta automaticamente no final do system prompt da sessão:"REGRA OBRIGATÓRIA DE DIRETÓRIO DE SAÍDA: Todos os arquivos finais, relatórios e entregáveis gerados nesta tarefa DEVEM ser salvos dentro do diretório <workspace>/output/2026-11/<task_slug>/. Nunca espalhe arquivos finais na raiz do projeto."
7.2. Integração Google Workspace (Dupla Camada: Nativa + MCP)
O OpenDesk integra os serviços do Google em duas frentes complementares:
1. Camada Pós-Processamento Nativa (em Rust):
   * Ao concluir uma tarefa ou rotina marcada com export_to_gdocs = true, o OpenDesk pega o artefato .md principal gerado, converte para a estrutura de documento e chama a API Google Docs / Drive para criar o documento formatado direto na pasta do workspace no Google Drive, salvando a URL de retorno em artifacts_provenance.google_doc_url.
   * Se a rotina ou tarefa gerar prazos/reuniões, sincroniza com a API do Google Calendar.
   * Notas rápidas na coluna de Backlog podem ser sincronizadas bidirecionalmente com o Google Keep / Google Tasks.
2. Camada de Ferramentas para Agentes via MCP (opendesk-mcp-bridge):
   * O próprio executável do OpenDesk expõe um subcomando opendesk mcp-google que implementa o protocolo MCP via stdio.
   * Ele é registrado automaticamente no opencode.jsonc do workspace, fornecendo aos agentes do OpenCode as ferramentas:
      * gmail_search_threads, gmail_create_draft, gmail_send_email
      * gdocs_read_document, gdocs_create_from_markdown, gdocs_append_text
      * gdrive_search_files, gdrive_upload_file, gdrive_create_folder
      * gcalendar_list_events, gcalendar_create_event
      * gkeep_list_notes, gkeep_create_note

10. Roteiro Sequencial de Implementação para o Agente de Desenvolvimento
Para construir o OpenDesk sem erros de compilação ou dependências quebradas, execute a implementação estritamente nesta ordem de fases:
Fase 1: Bootstrap do Core Rust, SQLite e Gerenciador do Daemon OpenCode
1. Inicialize o projeto Tauri v2 + React (TypeScript + Vite + Tailwind CSS).
2. Configure o Cargo.toml com tokio, axum, sqlx (sqlite, runtime-tokio), serde, serde_json, jsonc-parser, notify, tokio-cron-scheduler, reqwest (com stream), lettre, chrono, uuid.
3. Implemente as migrações SQLite (0001_initial_schema.sql) e os repositórios de banco de dados em src-tauri/src/db/.
4. Implemente daemon_manager.rs para verificar/iniciar opencode serve --port 3100 e consultar GET [http://127.0.0.1:3100/v1/models](http://127.0.0.1:3100/v1/models) (ou endpoint de modelos equivalente do OpenCode Server).
5. Implemente tray.rs criando o ícone na bandeja do sistema com status em tempo real e controles rápidos.
Fase 2: Motor SSOT e Sincronização Bidirecional de Arquivos (.opencode/)
1. Implemente jsonc_editor.rs capaz de ler e atualizar ~/.config/opencode/opencode.jsonc e <workspace>/opencode.jsonc preservando comentários.
2. Implemente agents_md.rs, skills_md.rs e commands_md.rs para listar, criar, editar e excluir agentes, skills e comandos diretamente no disco.
3. Implemente watcher.rs com a crate notify monitorando os diretórios de configuração e emitindo eventos via WebSocket.
4. Escreva testes unitários garantindo que criar um agente pela API Rust gera um arquivo .opencode/agents/<nome>.md válido que o comando opencode agent list reconhece.
Fase 3: Roteador Modular DSH, Fila de Execução e Interceptador de Artefatos
1. Implemente dsh_router/classifier.rs com suporte às políticas (COST_BENEFIT, CHEAPEST, BEST_QUALITY, MANUAL, CUSTOM_RULES) e separação Plan vs Build.
2. Implemente dsh_router/meta_builder.rs para permitir a criação de agentes, skills, comandos e MCPs via pedido em linguagem natural.
3. Implemente queue_scheduler/queue_manager.rs e budget_guard.rs com controle de concorrência, pausa, cancelamento e bloqueio por limite de orçamento.
4. Implemente opencode_client/stream_interceptor.rs para consumir o stream de execução do OpenCode (:3100), contabilizar tokens/custos em task_runs e registrar automaticamente na tabela artifacts_provenance todo arquivo criado ou modificado durante a sessão.
Fase 4: Agendador Cron, E-mail (SMTP) e Integração Google Workspace
1. Implemente cron_engine.rs lendo a tabela schedules, criando a pasta determinística <workspace>/output/YYYY-MM/<slug>/ e enfileirando a execução no horário programado.
2. Implemente smtp_mailer.rs para enviar o resumo e os arquivos gerados por e-mail ao término das tarefas/rotinas.
3. Implemente os clientes de integração Google Workspace (google_oauth.rs, google_docs.rs, google_drive.rs, google_calendar.rs, google_gmail.rs, google_keep.rs) e o subcomando MCP bridge para que o próprio OpenCode também possa usar essas ferramentas durante o loop de inferência.
Fase 5: Frontend Dark Mode (React + Tailwind + Shadcn/UI)
1. Construa o layout base com Sidebar, Topbar Workspace Switcher, Indicador de Orçamento, Controle da Fila e Command Bar global (Cmd/Ctrl+K).
2. Construa o Dashboard Executivo (cards dos últimos agentes com última tarefa, gráfico/tabela de gastos e uso por modelo, taxa de sucesso e atividades recentes).

11. Critérios de Aceite (Definition of Done para o Agente)
1. Paridade CLI ↔ UI: Criar um subagente @teste ou comando /teste na interface do OpenDesk deve criar instantaneamente o arquivo correspondente em .opencode/, e editar esse arquivo manualmente em um editor externo deve atualizar a tela do OpenDesk em menos de 500ms sem refresh manual.
2. Rastreabilidade de Artefatos: Toda vez que um agente criar um arquivo durante uma tarefa, o arquivo deve aparecer na aba Artefatos exibindo o nome do agente autor, a tarefa/prompt que motivou a criação, o horário exato e o diff do conteúdo.
3. Governança de Orçamento e Fila: Atingir o Hard Cap diário configurado deve pausar imediatamente novas execuções na fila e disparar uma notificação nativa no System Tray.
4. Entrega de Rotinas: Uma rotina agendada no Cron deve criar a pasta estruturada em output/YYYY-MM/, salvar os arquivos finais lá dentro e disparar o e-mail / sincronização com Google Docs configurados sem exigir nenhuma janela de chat aberta.
